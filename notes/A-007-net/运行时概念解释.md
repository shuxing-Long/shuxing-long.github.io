## 一、什么是"运行时"

### 直觉理解

你写的 C# 代码是**文本文件**（`.cs`），计算机无法直接执行。运行时就是**让代码"活起来"的那层基础设施**。

```
你写的代码（编译时）          运行时负责（运行时）
─────────────────────        ─────────────────────
class Program                • 分配内存存放对象
{                            • JIT 编译 IL → 机器码
    static void Main()       • 找到并加载依赖的 DLL
    {                        • 管理线程执行
        var s = "hello";     • 跟踪对象引用（GC）
        Console.WriteLine(s);• 处理异常、安全检查
    }                        • 在程序退出时回收所有资源
}
```

### 一句话定义

> **运行时（Runtime）** = 程序**正在执行时所处的环境**，它提供了程序运行所需的一切基础服务，让开发者不必从零实现内存管理、类型加载、线程调度等底层机制。

## 二、运行时 vs 编译时

| | **编译时（Compile Time）** | **运行时（Run Time）** |
|---|---|---|
| **发生阶段** | 写代码 → 编译器处理 → 生成可执行文件 | 双击 `.exe` → 程序开始执行 → 直到退出 |
| **主要工具** | 编译器（Roslyn / `csc.exe`） | 运行时（CLR / CoreCLR） |
| **代码形态** | 源码（`.cs`）→ IL 中间码（`.dll`） | IL → JIT 编译为 CPU 机器码 → 执行 |
| **类型检查** | 编译器检查类型是否匹配 | 运行时检查类型身份（同一类型在不同 ALC 中 ≠ 同一类型） |
| **能做的事** | 语法分析、静态类型检查、生成 IL | 创建对象、调用方法、加载程序集、垃圾回收 |
| **错误类型** | 编译错误：少分号、类型不匹配、命名空间不存在 | 运行时错误：NullReferenceException、StackOverflow、InvalidCastException |

### 关键区别：类型是什么？

```csharp
// 假设有一个自定义类型（定义在某个 DLL 中）
var obj = new MyPluginType();

// 编译时：编译器看到的是一个"类型名" MyPluginType
// 运行时：CLR 看到的是"类型标识" = [所在的 ALC] + [所在的程序集] + [类型名]
// 同一个名称 "MyPluginType"，在不同 ALC 中加载就是完全不同的运行时类型！
```

**举例**：宿主程序和插件各自引用了同名的 `MyPluginType`，但宿主的类型在 Default ALC，插件的类型在 Plugin ALC——两者在运行时被视为**不同类型**，即使字段完全一样也不能直接赋值或强转。

这也是 [ALC 与 BCL 概念笔记](#/viewNotes?id=A-007-net%2FALC%20%E4%B8%8E%20BCL%20%E6%A6%82%E5%BF%B5%E7%AC%94%E8%AE%B0) 中 ALC 隔离导致同名类型不兼容的根本原因。

## 三、.NET 运行时（CLR / CoreCLR）的核心职责

```
┌─────────────────────────────────────────────────┐
│                 你的程序 (.exe / .dll)             │
├─────────────────────────────────────────────────┤
│                 BCL（基础类库）                     │
│    System.String, System.IO.File, System.Linq   │
├─────────────────────────────────────────────────┤
│             运行时的六大核心子系统                   │
│                                                 │
│  ┌──────────┐ ┌──────────┐ ┌───────────────┐   │
│  │ JIT 编译器 │ │ 垃圾回收器 │ │ 程序集加载器   │   │
│  │ (RyuJIT) │ │  (GC)    │ │ (ALC 机制)    │   │
│  └──────────┘ └──────────┘ └───────────────┘   │
│  ┌──────────┐ ┌──────────┐ ┌───────────────┐   │
│  │ 异常处理   │ │ 线程调度   │ │ 类型系统      │   │
│  │          │ │          │ │ (Type Identity)│   │
│  └──────────┘ └──────────┘ └───────────────┘   │
├─────────────────────────────────────────────────┤
│               操作系统 (Windows / Linux / macOS)  │
└─────────────────────────────────────────────────┘
```

### 六大子系统的角色

| 子系统 | 做什么 | 在 ALC/BCL 笔记中的关联 |
|--------|--------|------------------------|
| **JIT 编译器** | 将 IL 中间码即时编译为 CPU 能执行的机器码 | BCL 的方法在首次调用时被 JIT 编译 |
| **垃圾回收器 (GC)** | 自动回收不再被引用的对象内存 | 当 `isCollectible` ALC 被 `Unload()` 后，GC 回收相关内存 |
| **程序集加载器** | 定位、加载、缓存 DLL 程序集 | **ALC 就是这个子系统的核心机制** |
| **异常处理** | 捕获和传播异常（try/catch/throw） | 跨 ALC 调用时异常需要能正确跨边界传播 |
| **线程调度** | 管理线程池、异步任务（Task）的执行 | `Channel<T>` 的读写、`Task` 的调度都依赖线程池 |
| **类型系统** | 维护类型标识，确保类型安全 | **类型标识 = ALC + 程序集 + 类型名**，是 ALC 隔离的底层支撑 |

## 四、BCL 与运行时

BCL（Base Class Library）是运行时**自带的**标准库。它不是运行时本身，但与运行时紧密绑定：

- BCL 随运行时一起安装（在 `C:\Program Files\dotnet\shared\Microsoft.NETCore.App\` 下）
- BCL 的类型在所有 ALC 中是**统一定义的**——`System.String` 不管在哪个 ALC 中引用，都是同一个运行时类型
- 这解释了为什么 [ALC 与 BCL 概念笔记](#/viewNotes?id=A-007-net%2FALC%20%E4%B8%8E%20BCL%20%E6%A6%82%E5%BF%B5%E7%AC%94%E8%AE%B0) 中说"跨 ALC 传 BCL 类型是安全的"

---

## 五、ALC 与运行时

ALC（AssemblyLoadContext）是运行时**程序集加载子系统**的核心抽象：

- 运行时通过 ALC 决定"从哪里加载 DLL"、"加载后如何缓存"、"何时可以卸载"
- 自定义 ALC（`isCollectible: true`）是运行时支持的**内存回收单位**——整个 ALC 及其加载的所有程序集可以一起被 GC 回收
- ALC 的隔离能力来自于运行时**类型系统**的保证：不同 ALC 加载的同名类型被标记为不同身份

本质上，ALC 是运行时对外暴露的**虚拟机级别的沙箱机制**。

## 六、对标其他语言的运行时

| 语言/平台 | 运行时名称 | 类比 |
|-----------|-----------|------|
| **.NET / C#** | CLR / CoreCLR | JIT 编译 + GC + 类型系统 |
| **Java** | JVM (HotSpot / OpenJ9) | 同样的 JIT + GC + ClassLoader |
| **JavaScript (Node.js)** | V8 引擎 | JIT + GC，但没有程序集加载的概念 |
| **Python** | CPython 解释器 | 解释执行（非 JIT），有 GIL |
| **Go** | Go Runtime | 编译为原生代码后仍携带着轻量运行时（goroutine 调度 + GC） |

---

## 七、一句话总结

> **运行时**就是你的程序从"硬盘上的死文件"变成"内存里活着的进程"所需要的全部基础设施。在 .NET 中，它就是 CLR。BCL 是它自带的工具箱，ALC 是它提供的隔离机制。

# .NET 异步编程中的同步上下文知识笔记

## 1. 什么是 SynchronizationContext

`SynchronizationContext` 是 .NET 中的**调度抽象**，表示“当前代码应该回到哪个上下文/调度器上继续执行”。

它不是线程本身，而是一套把回调派发到目标环境的机制。

核心 API：

```csharp
SynchronizationContext.Current
```

核心方法：

```csharp
public virtual void Post(SendOrPostCallback d, object? state);
public virtual void Send(SendOrPostCallback d, object? state);
```

- `Post`：异步派发回调。
- `Send`：同步派发回调。
- 默认实现通常把回调丢到线程池。
- UI 框架会提供自己的实现，例如：
  - WPF：`DispatcherSynchronizationContext`
  - WinForms：`WindowsFormsSynchronizationContext`
  - 旧 ASP.NET：`AspNetSynchronizationContext`

---

## 2. 与 async/await 的关系

`await` 默认会捕获当前 `SynchronizationContext.Current`：

```csharp
private async void Button_Click(...)
{
    var ctx = SynchronizationContext.Current;

    await Task.Delay(1000);

    // WPF/WinForms 中默认会回到 UI 线程
    TextBox.Text = "done";
}
```

规则：

- 如果 `SynchronizationContext.Current != null`，`await` 续体默认通过它的 `Post` 回到原上下文。
- 如果 `SynchronizationContext.Current == null`，续体通常交给线程池执行，**不保证回到原线程**。
- 如果 `await` 的任务已经完成，可能同步继续执行，不切换线程。

`ConfigureAwait(false)` 的作用：

```csharp
await Task.Delay(1000).ConfigureAwait(false);
```

告诉运行时不要捕获当前同步上下文，续体随便在线程池执行。

---

## 3. SynchronizationContext.Current 存的是什么

`SynchronizationContext.Current` 存的不是线程，也不是全局单例，而是：

> 当前线程、当前执行上下文关联的 `SynchronizationContext` 对象引用。

语义上可以理解为当前逻辑执行上下文中的一个调度器引用。它默认是 `null`。

可以通过代码设置：

```csharp
SynchronizationContext.SetSynchronizationContext(new MySynchronizationContext());
```

之后当前执行上下文中的 `SynchronizationContext.Current` 就会变成这个对象。

它和 `TaskScheduler.Current` 不同：

- `SynchronizationContext.Current`：决定 `await` 续体回到哪个上下文。
- `TaskScheduler.Current`：决定 `Task` 怎么调度。

---

## 4. 不同环境下的行为

| 环境 | `SynchronizationContext.Current` | `await` 后行为 |
|---|---|---|
| WPF / WinForms | UI 同步上下文 | 默认回到 UI 线程 |
| 旧 ASP.NET | `AspNetSynchronizationContext` | 回到请求上下文，容易死锁 |
| ASP.NET Core | 通常为 `null` | 不保证回到原线程 |
| 控制台程序 | 通常为 `null` | 不保证回到原线程 |

在 ASP.NET Core 和控制台程序中：

```csharp
Console.WriteLine(Thread.CurrentThread.ManagedThreadId);
await Task.Delay(1000);
Console.WriteLine(Thread.CurrentThread.ManagedThreadId);
```

两次线程 ID 可能相同，也可能不同，**没有保证**。

但 ASP.NET Core 中 `HttpContext`、`RequestServices` 等仍然能访问，因为它们依赖 `AsyncLocal`，不是线程亲和性。

不要用 `[ThreadStatic]` 或普通静态字段保存请求状态，应使用 `AsyncLocal` / `IHttpContextAccessor`。

## 5. 经典死锁

UI 线程中这样写可能死锁：

```csharp
var result = GetDataAsync().Result; // 阻塞 UI 线程
```

如果 `GetDataAsync` 内部 `await` 捕获了 UI 同步上下文，续体需要回到 UI 线程执行；但 UI 线程正被 `.Result` 阻塞，于是互相等待，死锁。

解决方式：

- 一路 `async/await`，不要混用 `.Result` / `.Wait()`。
- 库代码使用 `ConfigureAwait(false)`。
- UI 事件处理器中如果之后要更新 UI，通常不要随便 `ConfigureAwait(false)`。

---

## 6. 实践建议

- ASP.NET Core 和控制台程序默认没有同步上下文，`await` 后不保证回到原线程。
- 不要依赖线程 ID 或线程静态存储保存逻辑上下文。
- 库代码推荐使用 `ConfigureAwait(false)`，以兼容 UI 和旧 ASP.NET 环境。
- ASP.NET Core 中 `ConfigureAwait(false)` 通常没有额外效果，因为本来就没有同步上下文可捕获。
- UI 程序中，`await` 后默认回到 UI 线程，方便更新控件。
- 旧 ASP.NET 中要小心 `.Result` / `.Wait()` 导致的死锁。

---

## 7. 一句话总结

`SynchronizationContext` 是 .NET 中用于把代码回调调度回特定上下文（如 UI 线程）的抽象。`await` 默认会捕获它，从而决定续体在哪里执行。ASP.NET Core 和控制台程序通常没有同步上下文，所以 `await` 后一般不保证回到原线程；WPF/WinForms 等 UI 程序仍然存在同步上下文，并且对 UI 更新非常重要。
